## 何をするか

npmパッケージとして公開する前に、Bun専用API（テストコード以外での使用）を洗い出し、
Node.jsでも動かすのか・Bun専用として割り切るのかの方針を決める。

## 現状調査（2026-08-20時点）

- `src/`配下で`Bun.*`を直接呼んでいるのは`src/web/server.ts`の`Bun.serve()`のみ。
- `src/commands/web.ts`は`bun`バイナリをサブプロセスとしてspawnしており、
  webコマンドの実行にはBunランタイムそのものが必要。
- CLIエントリーポイント自体も`bun run src/cli.ts`前提で動いており、
  npmのbin経由でNode.jsから直接実行できる形にはなっていない。
- タスク/マイルストーンのCRUD部分（`store.ts`・`milestone-store.ts`・`task.ts`・`milestone.ts`）は
  `node:fs`等のNode標準APIのみを使っており、Bun専用API依存はなさそう。

## 検討事項

- `rrmap web`（Bun.serve依存）をNode.jsでも動く形に書き換えるか、Bun専用機能として
  「Bunがインストールされていないと使えない」と割り切るか。
- タスク/マイルストーン操作のコア部分（list/show/create/edit等）はNode.js単体で
  動作させたい（npm install後にNode.jsだけで使えることを想定）。

## 方針・意思決定

rrmap webもBun専用として割り切らず、Node.jsで動く形に書き換える方針にした。CLI本体（list/show/create/edit等）はもともと`node:fs`等のNode標準APIのみで書かれており対応不要だったため、実際に直したのはWeb UI（`Bun.serve()`依存）と`rrmap web`コマンド（bunバイナリのspawn依存）の2箇所になる。

`src/web/server.ts`から`Bun.serve()`を外し、`node:http`ベースの実装に書き換えた。タスク・マイルストーンのCRUDを扱うAPIハンドラーは`src/web/api.ts`に切り出し、Web標準の`Request`/`Response`を受け取って返す関数群にしてある。パスパラメータの取り出しには自作の簡易ルーター`src/web/router.ts`を使う。残るは`node:http`の`IncomingMessage`を`Request`に変換し、`Response`を`ServerResponse`へ書き戻すアダプタ層だけだ。これを`server.ts`内に置いたことで、BunでもNode.jsでも同じAPIハンドラーがそのまま動く。

フロントエンド（`index.html`・`app.tsx`等）は、BunのHTML importと`bun-plugin-tailwind`を通さないとTailwindのCSSが生成されない。これはビルド時の話であり、配布物の実行時にBunが不要であればよいので、ビルド・開発時にBunを使うこと自体は問題ないと判断した。そこで`scripts/build-web.ts`を新設し、`Bun.build()` APIに`bun-plugin-tailwind`を渡して`dist/web`に静的アセット（`index.html`、ハッシュ付きのjs/css）を出力するようにした。`package.json`には`build:web`スクリプトを追加した。

開発時のHMR体験を落とさないため、`src/web/dev-server.ts`を新設し、こちらは従来どおり`Bun.serve()`とHTML importを使う構成にした。ルート定義は`api.ts`のものをそのまま変換して使い回している。`package.json`の`dev`スクリプトはこの`dev-server.ts`を向くように変更した。

`src/commands/web.ts`は、これまでbunバイナリを`node:child_process`でspawnして`src/web/server.ts`を起動していたが、`server.ts`自体がNode.js対応になったため、spawnをやめて`import()`で同一プロセス内から直接起動する形に変えた。`dist/web`が無い場合は「`bun run build:web`を実行してください」という旨のエラーを出す。これで`rrmap web`コマンドの実行にbunバイナリは必須ではなくなった。

検証は`demo/`（rrmap自身のソースを含まない、タスクデータのみのディレクトリ）をcwdにして行った。Bun上で`src/web/server.ts`を起動し、`GET /`（静的HTML）・`GET /api/tasks`・`GET /api/milestones`・`PATCH /api/tasks/:id`が正常応答することを確認した。さらに`bun build --target=node`で`src/web/server.ts`をバンドルし、Node.js v24.19.0上で起動してAPIが正常応答することも確認した。`node:http`・`node:fs`等のNode標準APIのみで構成されているため、Bunが無くても動く。同様に`src/cli.ts`をバンドルしてNode.js上で`list`コマンドを実行し、CLI本体がもともとNode.js標準APIのみで書かれていたことも実証できた。加えて`bun test`で既存テスト29件全パス、`bunx tsc --noEmit`と`oxlint`も通過を確認している。

一つ残った課題はTASK-0011（配布形式の決定）に引き継ぐ。現状のソースコードは相対importの拡張子（`.ts`）を省略しており、Node.jsのESMローダーはこの省略を解決できないため、ビルドを経ずに`node src/web/server.ts`のように直接実行すると`ERR_MODULE_NOT_FOUND`になる。`bun build`でバンドルすれば問題なくNode.js上で動くことは上記で確認済みなので、配布時にはバンドルかtscコンパイルによるビルドが必須という前提でTASK-0011に着手してほしい。
